- **A/B/Z owners**: fake A with Available `123.45`, Held `20.00`; fake B with `7.00`/`0.00`; confirmed-zero Z. Add owner with no physical wallet: a successful read is virtual `0.00`/`0.00`, version 0, with no wallet initialization or bonus. Keep disabled/failed/denied reads distinct from this success. Bind wallet fixtures to actual `availableCredit`, `heldCredit`, `walletVersion`; no response owner/as-of field is invented. Values are safe test data, not seeded real accounts.
- **Exact amounts**: `0.00`, `0.01`, `12.34`, `9007199254740993.01` for pure formatting/precision tests. Large examples do not mean production policy permits such a top-up. VND invalid inputs include empty, `0`, `-1`, `1.5`, exponent notation and unsafe Number coercion.
- **Approved policy boundaries**: payOS, 1,000–2,000,000 VND inclusive in steps of 1,000, rate 1,000 VND/Credit and immutable quote lifetime 60 minutes are known backend policy. Exercise 1,000/2,000,000 valid and 999/1,001/2,001,000 invalid without rounding. These are policy/model checks, not live API evidence; create/status source now exists, standalone quote API does not. Never infer financial EXPIRED from client time or renew quote TTL on retry.
- **Payment fixtures**: future actual-contract fixtures require seven states including REVIEW, numeric version, nullable checkout/dates and exact quote strings; existing six-state P4/P5 fixtures remain historical preparation. Include unfamiliar state, wrong ID/owner, delayed/out-of-order reads, malformed response after server-side creation, lost creation response with/without known ID, confirmed no-creation rejection and reconciliation variants from accepted contracts.
- **Ledger fixtures**: at least 200 stable UUIDs over mobile limit 20 pages, equal timestamps, distinct server sequence order, overlapping IDs, new appends after first-page watermark, `type`/`referenceType` variants, all statuses and unknown type/state. Use actual DTO fields including HOLD amount `100.00`, Available delta `-100.00`, Held delta `100.00`, separate post-balances/operation/reference/reversal fields and creation time. Omit invented description/owner/entrySequence response fields. Backend accepts limit 1..100; mobile deliberately requests 20 within its existing parser max 50, with no shared parser change. No status filter is offered or sent.
- **QR fixtures**: synthetic raw-data payloads only, including long/dense/missing/invalid payload and local encode/render failure. Never use a raw payload as remote image/hosted URL/SVG markup or send it to a QR service. Payment-stage renderer selection must pass native/web compatibility and independent decoder equality against the exact input; no install or rendering claim is made here. Provider `providerStatus` must not become Payment `PAID`; closing QR is neither cancellation nor success.
- **Request controls**: deferred promises, call counters, session epoch changes, 401 renewal, network/protocol errors, simulated AppState/focus and gate/configuration changes. A loopback HTTP fixture must be bound to `127.0.0.1`, fake credentials only, and no production/gateway egress.

## Result recording and stop rules

- Future result rows must contain case ID, layer, commit/contract version, prerequisites/dataset, command/manual steps, expected and observed result, pass/fail/blocked status and safe evidence path. Counts must distinguish HTTP requests, logical intents and backend ledger postings.
- Never commit credentials, tokens, real QR payloads, raw provider payloads or actual private account histories. Use synthetic QR/data or redacted minimal references sufficient to audit results. Implemented Payment source/protocol/policy does not close mobile integration, retention/restart, QR/channel or deployed posting evidence gates; no hosted checkout/return/cancel page is required and no sandbox hostname is invented.
- V27/V28/V29 remain blocked if their environment/owner/provider/native prerequisites are missing; they cannot be replaced by the corresponding fixture case.
- Application checks: focused tests plus mobile lint/type/structure and relevant full-suite regression after source implementation. Web export is a bundle/build check, not native acceptance.
- Any false success, unintended new create, other-owner disclosure, precision loss, denied-cache resurrection or duplicate ledger posting blocks the affected stage regardless of unrelated passing tests.
