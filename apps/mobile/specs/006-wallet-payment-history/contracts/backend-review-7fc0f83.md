## Material mobile drift

1. `apps/mobile/src/features/wallet/schemas/payment-contracts.ts:37–81` and `types/payment.ts:18–31` currently omit the new recovery fields. Existing parsing ignores extra properties, so old tests can pass while silently discarding safety context. Update contract fixtures/tests before schema/types; retain exact strings, nullable dates/checkout, REVIEW and unknown handling.
2. `utils/payment-observation.ts` accepts numeric version ordering and latches QR-null, but does not project recovery metadata. New tests must separate mutable read-time safety metadata from immutable identity/quote. An accepted current-ticket same-version response can change recoveryRequired/recoveryReason without being an immutable conflict. Old tickets/lower versions never undo newer data; same-version QR-null remains latched even if configuration later restores eligibility. A current reason can clear without restoring that QR. Contradictory/unknown metadata remains safely unavailable for create/QR, not fabricated Payment failure.
3. `api/payment-api.ts` currently implements owner list/detail only. Add policy GET and explicit create/replay only in a later implementation request. Normal WalletProvider enables wallet/history/transaction only; Payment flags stay false. Existing US3 status integration remains independent of US2 create/storage/QR.
4. Backend409 may include `details.existingPaymentId`; mobile `src/lib/http/response.ts:12–21` and AppError currently discard details. Recommended plan: use the retained local ID or an explicit authenticated creation-policy GET after the conflict to discover a current own blocker, then owner GET. This GET is not a replay and not proof that a blocker matches a lost intent. If no ID/policy is unavailable, keep support/unknown state. Do not silently invent error.details support or widen shared HTTP/pagination. Any later additive shared-error design requires explicit task ownership and consumer regression.
5. Payment list starts from checkout rows (`read-payments.use-case.ts:119–137`); a legacy Payment without checkout can be absent from every list page while policy still blocks and detail is readable by the supplied own ID. Empty/full-list discovery never authorizes a replacement.
