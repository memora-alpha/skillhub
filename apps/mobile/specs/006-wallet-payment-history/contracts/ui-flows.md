## Common presentation and entry rules

- Preserve six existing real wallet routes and authenticated gating. Home and own Profile already have a wallet route mapping. Return through actual navigation history where available; direct links fall back to wallet/history, not an arbitrary external return URL.
- Route params identify navigation context only. `state=success`, a VND `amount`, a sample ID or an arbitrary gateway URL never becomes a financial observation or trusted destination. Validate required identity against the actual capability contract before a live read.
- Initial loading, disabled/unavailable capability, confirmed zero/empty, content, same-owner stale refresh, error and denied/not-found are separate. A disabled query with no data is not an empty account.
- Keep confirmed same-owner content during transient refresh failure with an updating/stale notice. After owner denial or session change, remove that private projection; transient errors cannot restore it.
- Reuse theme, text/amount typography, shell, controlled inputs, Button, FormNotice and existing focus/keyboard conventions. New native menus/pickers/sheets must first check installed `@expo/ui`; no new UI library is justified. History needs a virtualized feature-owned list rather than nesting inside a scrolling FeaturePage.
- Use readable Vietnamese labels, explicit CR/VND units, accessible names/disabled/busy state and non-color status text. Announce meaningful outcome/error changes without repeatedly announcing every refresh. At 320 logical pixels, allow long IDs/amounts to wrap or be selectable without hiding primary actions.
- Product copy describes user actions and outcomes, not API gaps, idempotency internals or provider exception details. Technical dependency IDs belong to planning/evidence, not end-user error screens.

## US2 — Amount, review, creation and in-app payOS QR

**Current capability**: approved policy and pure payOS adapter exist; operational Payment create/query/recovery does not. Below is a gated UI contract, not a live API.

| Step        | Preconditions and action                        | Confirmed display / result                                                                                                           | Failure, retry and exit                                                                                                               |
| ----------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| T1 Prepare  | Auth ready; open top-up                         | payOS only, integer VND, approved1,000–2,000,000/step1,000 and rate1,000; no invented preset catalog                                 | Missing operation shows unavailable real Confirm; local policy/model preview is explicitly labeled.                                   |
| T2 Validate | No unknown creation; edit amount                | Validate approved exact bounds/step, preserve draft; do not use Number rounding                                                      | Inline invalid input; no unsupported real submission.                                                                                 |
| T3 Review   | Valid draft; continue                           | VND/payOS/rate and estimated versus backend-confirmed Credit; server quote policy/version/expiry when actually provided              | Changed authoritative quote requires re-review, not automatic confirmation; no create while unavailable.                              |
| T4 Create   | Operational gates and review satisfied; Confirm | One runtime claim/immutable intent, pending text, duplicate action disabled                                                          | Uncertain dispatch retains unknown intent; no fresh-key retry. Valid owner ID is creation success, not payment success.               |
| T5 QR       | Known owner payment; actual prepared descriptor | Encode exact raw qrCode locally through vetted encoder and existing SVG renderer; separate preparing/null, ready and render-error UI | Retry render or known-payment read, never create again. No remote QR service, image URL, SvgXml, hosted checkout, WebView or browser. |
| T6 Observe  | Leave QR, switch apps or open status            | Read exact known owner Payment only when API exists; QR/providerStatus does not determine financial result                           | Closing screen does not cancel/fail/expire; safe Back preserves runtime identity, status errors remain read errors.                   |

Before dispatch, Back preserves the active-session draft. While immediate create is active, guard accidental route removal with existing navigation facilities; if UI detaches, session runtime retains the intent. Unknown creation allows safe return to wallet/history but blocks another creation until reconciled. Known PENDING is not unknown creation; do not invent a universal one-pending-payment rule.

QR-01 requires local encoder version/license/native-web validation and independent decode-to-exact-payload proof, including long/dense payload, quiet zone, contrast, integer module sizing and 320px layout. QR receives accessible payment context, amount and status; it is not a scanner. Raw payload/descriptor must not be logged, placed in URLs or persisted as credentials.

The 60-minute quote expiry is server-authored and immutable. A countdown, if later supported, is presentation only: no TTL renewal on refresh/retry, no local EXPIRED/FAILED/cancel and no automatic replacement payment. No return/cancel screen or bank-app deep link/save/share/scanner permission is part of this scope. Validate a supported scanning workflow and document same-device limitations rather than promising unsupported actions.

## US4 — History and detail

Actual read contract: [wallet-http.md](wallet-http.md). Preserve descending committed ledger-sequence order from the server; timestamps/UUIDs are display/identity, not a replacement sort key.

| Step            | Preconditions and action                                           | Confirmed result                                                                                                     | Failure/retry and exit                                                                                      |
| --------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| H1 List         | Auth ready; open history with explicit limit20                     | Actual owner page, exact amount/deltas, type/status/time; empty only from successful response                        | Loading/error/denial distinct; no fixture fallback.                                                         |
| H2 Filter       | Select type/referenceType or clear                                 | New filter-specific identity and cursor-free first page; criteria applied by backend across history                  | No status/date/search parameter or client partial-page filtering.                                           |
| H3 More         | Current chain has opaque nextCursor; no replacement refresh active | Preserve server order and dedupe by ID; entries remain below captured watermark                                      | Later-page failure preserves earlier pages; retry read only. Invalid cursor400 offers fresh-chain recovery. |
| H4 Refresh      | User refreshes or relevant focus refresh                           | Start without cursor, capture new high-water snapshot, discard/rebuild prior continuations; new append appears here  | Keep clearly stale same-owner content during read failure; never mix new first page with old cursor pages.  |
| H5 Detail       | Contract-valid UUID                                                | Owner-authorized actual row plus operation/reference/reversesTransactionId/deltas/post-balances; no fake description | Missing/nonowner404 evicts detail; subsequent transient error cannot restore denied data.                   |
| H6 Context/Back | Inspect supported fields or use Back                               | Safe raw reference display and contextual history return; supported authorized links only                            | Missing/preview-only destinations omitted; do not feed real IDs into samples or infer held allocations.     |

Backend permits limit1–100/default20; mobile page parser permits1–50. Explicit20 is a compatible subset and needs no shared parser change. Cursor is opaque, signed and bound to owner/type/referenceType, not session/limit; no client cursor TTL or decoding. Keep page size fixed per chain.

Status is displayed per actual row but not offered as a real filter. Amount is magnitude; Available/Held deltas carry separate effects. Pending/failed payment is not fabricated as a ledger row; reversal keeps original immutable history, and no cash-out/refund/admin/settlement action is exposed.

## Preview separation contract

1. Normal wallet routes are live/unavailable, never automatic fixtures. Setting `demo=false` without replacing sample data is insufficient.
2. Preserve gallery scenarios in a labeled preview host with injected local models and no live financial client. `UiPreviewProvider` currently hosts live request infrastructure; its name is not a sufficient boundary.
3. Retarget gallery/sample Credit notice to that host or a clearly unavailable sample action. Keep notification API integration outside scope. A `tx-topup` or `state=success` link in the real flow cannot display a fake record/outcome.
4. A preview must never create a live payment, use real merchant QR payloads or gateway destinations or write a real account cache. Test the boundary by asserting no production-bound request/mutation egress.
5. Model fixtures may exercise QR/status before Payment APIs exist. Wallet/history loopback fixtures can now match the actual read contract; future Payment HTTP fixtures still require an implemented contract. Every fixture remains labeled test evidence.
