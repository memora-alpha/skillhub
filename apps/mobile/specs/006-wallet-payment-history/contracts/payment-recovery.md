# Payment intent, observation and recovery contract

**P5 preparation checkpoint — 2026-10-17**: T044..T051 implement only injected owner observation/related-read models and safe unavailable UI. US3 has no US2 coordinator dependency. Same identity/owner/session and expected exact money are required; unfamiliar state is neutral. With no accepted freshness mechanism, changed observations produce a conflict notice around the previous stale result; no enum ranking or client clock decides which is newer. Denial evicts the private observation. Related refresh records each read independently and cannot roll PAID back, add Credit or synthesize ledger data. Normal mode configures no reader or financial recovery operation. The checkpoint below describes P4 history; operational protocols remain proposed where not explicitly implemented as local models.

## Creation protocol

1. Validate current authenticated owner and confirmed capability/policy; make an exact reviewed snapshot. No request is sent from an invalid/unavailable form.
2. On explicit Confirm, synchronously claim one runtime intent before the first await. A second caller/remounted screen observes the same claim; it does not generate a new request/key.
3. Assign one intent identity and, only under the actual payment contract, its idempotency/correlation key. Freeze submitted amount, method and any required confirmed review data. Do not infer intent identity from equal bodies.
4. Dispatch through shared authenticated HTTP with AbortSignal, `retry:false` at mutation ownership and explicit `replayAfterRenewal:false`. This is local design, not proof of server idempotency. No automatic offline queue.
5. Validate the returned projection before publishing identity/result: shape, exact money, requested association and owner/session still current. A malformed successful response may follow a committed server payment and therefore produces unknown outcome, not permission to create again.
6. Valid confirmed creation stores the payment ID and permits contracted local QR preparation/display and owner status read. It does not increment wallet or mark paid. Proven no-creation rejection permits a corrected review only according to accepted semantics.
7. Uncertain dispatch outcome keeps the intent frozen, releases only the transport busy indicator and enters UNKNOWN_OUTCOME. The creation lock's unresolved condition remains even though no request is currently in flight.
8. Reconcile the same intent via the agreed mechanism. A safe same-key replay is permitted only if GAP-06 explicitly establishes it; do not change key/body or automatically execute it on reconnect/foreground.
9. Clear/retire an intent only after confirmed resolution and a deliberate next user action. Never retire solely on component unmount, timeout, QR screen closure or an error toast.

Resolution here concerns the creation result/identity. Once a payment is known, its financial status may remain `PENDING`; that alone does not establish a Product rule forbidding another explicit intent. Follow accepted endpoint/method restrictions instead of inventing a one-pending-payment policy. An unknown creation remains blocked until reconciled.

## QR preparation and render states

The pure payOS descriptor contains paymentLinkId/qrCode/orderCode/providerStatus, not a hosted URL. The proposed future owner API may have preparing/null checkout; that wire behavior remains unimplemented. Keep preparation/readiness, local encoding/render success/error and owner Payment status separate. Encode exact raw payload locally, independently decode the rendered QR to validate it, and never treat providerStatus as the financial observation. No remote image/QR service, SvgXml/HTML/Linking interpretation or return/cancel page.

A render retry uses the same known payment and payload; closing QR does not cancel it or decide failure/expiry. Clear raw payloads on session disposal and do not log or publish them. Approved quote TTL60 minutes belongs to the immutable server quote, not a timer restarted by refresh or a locally calculated Payment state. QR-01 and supported scan usability must be resolved before end-to-end payment acceptance; no scanner, save/share or bank-app action is assumed.

## Concurrency boundaries

- **Before dispatch**: Synchronous runtime lock protects same-tick double taps and multiple create callers. Button pending state is secondary feedback.
- **Across navigation**: Runtime lives above the six wallet views and Home; screen remounts attach to the current intent rather than instantiate one. Navigation must not silently clear unknown outcome.
- **Within one session**: Each status/read identity has a monotonically increasing request ticket; superseded responses cannot overwrite newer observations. Query cancellation is combined with forwarded AbortSignal and current-session/request guards.
- **Across sessions**: Cleanup invalidates runtime immediately, aborts listeners/queries, removes scoped cache and clears private drafts/intents. A late response cannot update, replay against or expire a different session. Backend recovery is required if the owner later returns after an unresolved creation.
- **Server boundary**: Aborting an HTTP request cannot undo a server commit. A client lock cannot guarantee exactly-once provider posting. Both properties require the backend contract and sandbox/concurrency evidence.

## Status observer and related refresh

- Manual status checking is baseline; one active check per payment identity. A screen attaches/detaches without changing payment state.
- Focus/foreground may re-read known owner payment identity and wallet data; no create or verify mutation is inferred. If a future contract requires a verify mutation, revise its ownership/idempotency/tests explicitly.
- Default Query stale time does not mean the balance is current enough for a payment decision. Show read freshness and explicitly refresh after confirmed PAID; do not optimistically patch amounts.
- Keep payment observation separate from the two related refresh results. Either wallet or history may succeed/fail independently. Use independently settled read results so a history failure cannot turn verified payment success into failed creation.
- No scheduled polling is enabled by this plan. If later agreed, record exact cadence/backoff, finite request/wait budget and rate-limit handling. Pause in background, detach on blur, stop on session/identity change or confirmed terminal/unknown state. Never turn budget exhaustion into server expiry.
- A previously PAID payment may later be read as REFUNDED only from an authoritative permitted observation. Do not build a local transition engine from enum ordering.

## Cleanup and safe persistence boundary

On logout/owner-generation change: immediately invalidate scope; hide financial content; detach AppState/focus listeners; invalidate request tickets; abort forwarded reads; cancel/remove only wallet queries; clear private drafts/intent IDs/raw QR descriptors. Ignore late callbacks even if abort is ineffective.

Do not put wallet balances, payment responses or unresolved intent payloads into the credential store merely to claim durability. GAP-06 must establish the chosen correlation/retention/recovery mechanism and cross-session behavior first. If a durable marker is later justified, add its minimal data, owner binding, clear/expiry policy and security tests as an explicit design revision rather than silently adding storage.

## Financial activation gate

Before real Confirm/QR payment continuation is enabled, require: implemented create/quote contract, same-intent replay/reconciliation semantics including lost ID, owner status lookup, authoritative expiry/verification rules, QR-only owner projection/local encoder validation, restart recovery decision, and approved payOS channel/backend proof of verified atomic single top-up posting. Provider/range/step/TTL are already selected; they do not supply these missing operations. No sandbox host, real transfer or merchant activation is invented by planning. UI fixtures cannot close these gates.
