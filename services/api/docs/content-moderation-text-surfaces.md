# Content moderation for additional text surfaces

These routes run the check in the owning application service before writing the submitted text. `off` preserves the existing write flow. `observe` allows the write and records the classification outcome. In `enforce`, blocked text returns `422 CONTENT_MODERATION_BLOCKED` and a provider outage returns `503 CONTENT_MODERATION_TEMPORARILY_UNAVAILABLE`.

| Surface | API write | User-entered fields | Audience and version check |
| --- | --- | --- | --- |
| `profile` | `POST /auth/register`, `POST /auth/verification/verify` | `fullName` | The encrypted OTP draft carries the checked name and enforcement policy version. Verification checks drafts staged before enforcement before creating the account. The public profile and display names read the stored account name. |
| `profile` | `PATCH /me/profile` | `fullName`, `headline`, `bio` | Public profile and display names read the submitted patch from the account. The final write checks the session under the user's row lock. Blank and omitted fields require no provider call. |
| `sharing_skill` | `POST /me/skills`, `PATCH /me/skills/:sharingSkillId`, `POST /me/skills/:sharingSkillId/restore` | `description`, including an existing description when making a hidden or archived skill public | Public skill search and profiles read the description. Changes and restore recheck `expectedVersion`. Completed keys replay after authorization. |
| `sharing_skill` | `POST /me/skills/:sharingSkillId/verifications` | Evidence `title` and `description` | Staff reviewing skill evidence can read these fields. The write rechecks active ownership and the pending-request constraint. Completed keys replay after authorization. |
| `tag_request` | `POST /tag-requests` | Normalized `label` | Staff approval reads the immutable requested label and uses it for the public catalog entry. Completed keys replay after authorization. |
| `proposal` | `POST /proposals`, `PATCH /proposals/:id` | Normalized `message` and `candidateSlots` | Both participants read the proposal. Updates recheck status, expiry, and `expectedVersion`. Proposal events reference the committed row. Completed keys replay after authorization. |
| `learning_path` | `POST /learning-paths/:pathId/plans`, `PATCH /learning-paths/plans/:planId` | `learningGoal` and each `sessionOutline[].content` | Both path participants read the plan revision, including outlines later used as session content. The write rechecks the applicable agreement and plan versions. An identical revision reuses the current plan. |
| `learning_path` | `POST /learning-paths/:pathId/termination-requests`, `POST …/:requestId/response`, `POST …/:requestId/escalate` | Request `reason`, response `note`, escalation `reason` | Participants read the request and response. Staff review and audit use the committed transition. Create replays by the existing key. Response and escalation recheck the request version, response identity, and open state according to the existing transition rules. |
| `session` | `POST /sessions/:sessionId/cancellation-requests`, `POST …/:requestId/response` | Request `reason`, response `note` | Participants read the request and response. Creation validates the expected occurrence and replays by key. A response rechecks the request version and existing response. |
| `session` | `POST /sessions/:sessionId/absence-excuse`, `POST …/absence-excuse/decision`, `POST …/confirm-completion` | Absence `reason`, decision `note`, completion `note` | The session stores the text under its existing participant permissions and outcome. The final transaction rechecks the occurrence, current outcome or excuse, and relevant deadline. Repeated completion confirmations reuse the existing result. |

Schedule proposals and reschedules accept session numbers, timestamps and expected versions. Free-form scheduling suggestions are `candidateSlots` on a Proposal. Payment creation accepts an amount and a defined payment channel. System cards and notifications reference the committed source record or use fixed templates. Moderator decisions and the dedicated Report intake follow their own workflows.
