# Identity data model

The identity model is represented in [prisma/schema.prisma](../../prisma/schema.prisma): 14 identity models and 8 identity enums, within the complete relational catalog (45 models and 25 enums); see [schema catalog](../../prisma/README.md). Message/MessageAttachment are MongoDB reference models; runtime remains Mongoose. Identity state belongs to PostgreSQL with UUID IDs and UTC `timestamptz`. The identity-only migration and use cases now exist; later catalog migrations remain deferred. See [validation](validation.md) for the disposable PostgreSQL verification and deployment limits.

Profile is sole fullName/timezone/locale authority; accountStatus belongs only to User. Metrics are derived/system-owned; later skills/sessions/reviews owners define synchronization contracts before updating. Nullable reputation means uninitialized, not zero; production requires approved initialization. OAuthAccount/CHANGE_EMAIL are now present for full catalog coverage but their endpoints remain deferred from this identity feature.

## Indexes and invariants

- Normalized email check and unique index enforce races without app-only validation.
- Challenges indexed userId/purpose/createdAt and expiry; partial unique outstanding unsuperseded/unconsumed challenge per user/purpose. Expired challenge explicitly superseded before replacement (expiry alone cannot participate in a time-dependent index).
- Session index userId/revokedAt/expiry; token digest unique and generation composite unique. History purged only after family expiry and approved retention.
- Due delivery status/nextAttemptAt and lease expiry indexed; intent dedupeKey unique. Queue contains only IDs.
- User list keyset `(createdAt,id)` and status/role filters; no token/challenge endpoints.
- Avatar selection must reference same-owner CLEAN asset: composite owner/asset FK plus locked selection use case; direct client metadata writes forbidden.
- SQL CHECK constraints and outstanding-challenge partial uniqueness must be added to a reviewed migration and verified against real PostgreSQL. Prisma supports partial indexes behind the `partialIndexes` preview flag; this schema keeps the existing stable generator configuration and leaves that index to migration SQL. See [Prisma index documentation](https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/indexes#configuring-partial-indexes-with-where).

## Prisma representation and remaining enforcement

- Models use snake_case table/column mapping, native UUID/bytea and UTC timestamps. Composite keys implement UserRole, RolePermission and OtpIssueWindow; digest/dedupe/email/storage uniqueness and query indexes are explicit.
- Profile owns display name/timezone/locale; optional selected avatar uses a composite `(userId,avatarAssetId)` FK to `(userId,id)` to prevent another owner's image. CLEAN state still needs locked use-case validation.
- ReauthProof has both User FK and composite `(userId,sessionId)` FK to RefreshSession `(userId,id)`, preventing a proof bound to another user's session.
- Digests and authenticated ciphertext are Bytes; protected recipient is `encryptedRecipient`, payload is `encryptedPayload`, with external encryption keys identified by `encryptionKeyId`. Encryption/redaction are application responsibilities, not automatic Prisma behavior.
- Defaults encode only planned technical/SRS states: pending signup, false verification, zero counters, vi locale, pending delivery and quarantined upload. No default terms version, timezone, initial reputation, TTL, Admin account or Staff permissions is invented. Reputation remains nullable.
- Foreign keys use Restrict on deletion so account deletion cannot cascade credentials/audit/delivery history silently. Approved cleanup must explicitly remove eligible dependents in a safe order; account hard deletion is outside this feature.
- Profile relation is optional on the User side because Prisma cannot guarantee every User has a Profile; signup must create both atomically. Role definitions/grants need idempotent seed/operator flows, not schema defaults.
- Implemented SQL CHECKs: normalizedEmail lower/trim/no whitespace and 5–254 characters; nonnegative counters/generations/attempts/securityVersion; reputation 0–100 when present; fullName minimum length; avatar size 1–5 MB and allowed MIME; chronological expiry and compatible proof/delivery state fields. Application policies additionally enforce IANA timezone, password/OTP rules, legal transitions, fresh grants, one-use consumption and payload erasure; the migration makes audit append-only.
- IdentityEmailDelivery user/challenge references are individually valid FKs; scheduling use cases must also check that challenge belongs to the recipient User and that kind/purpose agree. Leases/attempts/idempotency still require transactional worker logic.

Implementation follow-up: identity migration/SQL constraints and seed/bootstrap now exist and were verified against disposable real PostgreSQL schemas; see [validation](validation.md). The complete catalog still includes future, unmigrated models. No live application-schema deployment has been performed.

## State machines

| Aggregate | Transitions                                                                                                                                                      |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account   | register→PENDING; REGISTER consume→ACTIVE; authorized lock ACTIVE→LOCKED; unlock verified LOCKED→ACTIVE; SUSPENDED/DEACTIVATED have no new transition route here |
| Challenge | issued→consumed/superseded/exhausted/expired; never reused; server checks expiry on consume                                                                      |
| Session   | created→rotated generations→revoked/expired; used-token replay revokes only family                                                                               |
| Reset     | valid RESET proof→password/securityVersion/all-session revoke/audit/change email atomically; only ACTIVE/LOCKED/SUSPENDED eligible; preserves status             |
| Avatar    | QUARANTINED→CLEAN/REJECTED; unreferenced/expired→DELETED via retryable cleanup; clean selection atomic                                                           |
| Delivery  | PENDING→LEASED→SENT; bounded retry→PENDING; terminal FAILED/EXPIRED/CANCELLED; scrub temporary secret                                                            |

Lock User rows first (sorted actor/target IDs), then challenge/session/authorization rows consistently. Issue/revoke operations recheck status/hash/version under same lock; no stale login/refresh survives reset/lock. Actor grants and one-use reauth validated within privileged transaction. Audit failure rolls back mutations. Failure counters and replay revocation commit before returning domain error. Requests admitted before revoke may complete; requests authorized after commit must fail. External provider calls occur outside DB locks, with outbox/compensation for recovery.
