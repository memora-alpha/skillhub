# SkillHub Entities and Fields v2

Field catalog for SRS 1.5 with the user's scope adjustments. Generated by `generate_data_models_v2.py`.

This is a logical design, not an inventory of deployed tables. Definitions match the single-canvas `SkillHub_Logical_Data_Model_v2.drawio`, using the v1 presentation style.

48 PostgreSQL tables and 1 MongoDB document concept. SessionAttendance summaries are merged into Session. SkillTag and its request/material joins are removed; SkillCategory and Skill remain. Profile fields are merged into User; PathSettlement fields are merged into LearningPath. Eight owned models are merged into their parents: version/session confirmation fields, suggestion arrays, Session room metadata and embedded Message attachments. MaterialVersion is removed: current file metadata is on Material, purchased file snapshots are on MaterialOrder. Each User has exactly one Role through required users.role_id; UserRole is removed. Achievement, selected title and OTP structures are excluded by user decision. Existing identity helpers are retained; history/join/operation structures implement requirements using proposed normalization.

PK = primary key; FK = same-store relational reference; UQ = column uniqueness; NN = required. REF = application reference without a PostgreSQL FK. Composite uniqueness and checks are specified in `SkillHub_Logical_Data_Model_v2.md`.

Credit BIGINT values are hundredths of Credit (100 units = 1 Credit). VND and file sizes are unscaled integers. TIMESTAMP means UTC. ENUM values not listed inline are defined by the accompanying constraints/state vocabulary; open policies are not invented defaults.

Diagrams list one field per row, like v1. This catalog is a logical design, not executable DDL.

## Identity

PostgreSQL | Profile fields merged into User; no Profile table. One Role per User; Reputation starts at 50 (range 0-100). Composite avatar/proof ownership checks required; selected avatar must belong to the same User. Public profile responses project only allowed fields, excluding identity secrets/security metadata. Reputation and counters remain server-managed.

## Learning agreements

PostgreSQL | TWO_WAY: exactly A->B and B->A plans, each learner confirms, then A+B confirm the same pathVersion. ONE_WAY: one teacher->learner plan. Immutable snapshots; 20 Credit/User applies to whole TWO_WAY agreement, not each plan. Confirmation timestamps are nullable fields on each version; actors derive from fixed plan/path participants. New versions start unconfirmed. PathSettlement is merged into LearningPath: settlement fields all NULL before settlement, all required after settlement. Unique settlement_operation_id; composite (path_id, settled_path_version) FK to owned PathVersion. One immutable final settlement/path, atomically with ledger/wallet/allocation/status; lock the path and guard settled_at IS NULL for concurrent retries.

## Scheduling and sessions

PostgreSQL | Duration 60-180 minutes. One stable Session per plan outline; schedule history preserves reschedules. Two confirmations >=60 minutes before old startAt. Pending revision does not replace applied schedule or HOLD again. No per-session settlement. ScheduleVersion stores A/B confirmation timestamps. Session stores teacher/learner confirmation status, timestamp and note, plus unique nullable room_name, provider_room_id and room_metadata. No room secrets/tokens. SessionAttendance is merged into Session: teacher/learner first_joined_at, last_left_at and attendance_seconds (nonnegative, default 0). Timestamps nullable until observed. Duration is actual connected time summed across reconnects, not lastLeft-firstJoin; avoid overlapping connection double-counts. Only verified provider data updates summaries; ingestion must handle duplicate/out-of-order events. No detailed join/leave history is modeled; attendance does not complete a Session.
